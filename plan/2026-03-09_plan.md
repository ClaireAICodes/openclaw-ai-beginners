### 1. OpenClaw Health Monitor & Auto-Recovery System (GREEN)

**Impact:** High | **Effort:** 10 hours | **Confidence:** High

**Overview:**
A lightweight monitoring system that proactively checks the health of critical OpenClaw operations (cron jobs, backups, agent status, disk space) and automatically attempts recovery for known issues (retry failed backups, restart stalled agents). Provides a local dashboard endpoint and Telegram alerts, preventing silent infrastructure failures.

**Resource Requirements:**
- 🆓 Free hosting: Runs as OpenClaw cron job (no external hosting)
- 🆓 Free APIs/models: OpenRouter free tier (step-3.5-flash:free) for log pattern analysis
- 🧰 OpenClaw Skills needed: `exa-tool` (for log fetching), custom `health-monitor` skill
- 💸 Costs: $0
- 🔑 Master must provide: None (uses existing Telegram integration)

**Prerequisites:** None - can start immediately

**Feasibility Assessment:**
- ✅ Can build autonomously with current resources
- Uses existing OpenClaw cron, Telegram, and file system
- No external dependencies

**Detailed Implementation Steps:**

1. **Setup Phase** (1.5 hours)
   - Create new skill directory: `skills/health-monitor`
   - Define health check targets:
     * Cron jobs: check last run times via `cron list` and log freshness
     * Backups: check existence and size of latest backup files in `backups/`
     * Agents: check sub-agent status via `subagents list`
     * Disk space: check available space on workspace volume
     * Log errors: scan recent logs (`logs/*.log`) for ERROR/FATAL lines
   - Design alert severity levels: CRITICAL (auto-recovery), WARNING (notify), INFO (log only)
   - Define recovery actions:
     * Stalled cron: send wake event via `cron wake`
     * Failed backup: retry with exponential backoff (max 3 retries)
     * Stalled agent: restart via `subagents kill` + restart if appropriate
     * Disk full: cleanup old logs (>30 days), notify CRITICAL

2. **Development Phase** (6 hours)
   - Implement health check functions:
     * `checkCronHealth()` - query cron status, detect missed runs
     * `checkBackupHealth()` - verify backup files exist, not corrupted, timestamp <24h
     * `checkAgentHealth()` - verify long-running sub-agents are responsive
     * `checkDiskSpace()` - ensure >1GB free, alert if <5GB
     * `checkErrorLogs()` - scan for ERROR/FATAL in last 24h
   - Build decision engine:
     * Score overall health (0-100)
     * Determine if auto-recovery is safe (based on action type and failure frequency)
     * Implement recovery loop with jittered retries
   - Create alert system:
     * Send Telegram messages with appropriate severity
     * Include health score snapshot, failing checks, recovery actions taken
     * Rate limit alerts (max 1 per hour per issue type)
   - Build persistence:
     * Store health history in `monitoring/health-state.json`
     * Track trends, prevent recovery loops
   - Create dashboard endpoint:
     * HTTP server on localhost:PORT/health (use Node's `http` module)
     * Return JSON health status and recent history
     * Simple HTML view at `/health?format=html` for quick checks

3. **Testing Phase** (1.5 hours)
   - Simulate failures: stop a cron job, corrupt a backup file, fill disk with temp file
   - Verify detection and appropriate recovery actions
   - Test alert throttling
   - Validate dashboard output and history tracking

4. **Deployment Phase** (1 hour)
   - Install skill: `skills/health-monitor/index.js` entry point
   - Configure cron: every 30 minutes (0,30 * * *)
   - Set up initial state file and log directory
   - Add to `HEARTBEAT.md`: Quick check of health score each heartbeat
   - Create recovery log: `monitoring/recovery-actions.log`

5. **Maintenance Phase** (ongoing, 30min/week)
   - Review false positives/negatives weekly
   - Adjust thresholds (e.g., disk space, timeout values) based on actual usage
   - Add new checks as needed (e.g., API rate limit monitoring)
   - Update recovery actions if new failure modes emerge

**Potential Blockers & Mitigations:**
- Auto-recovery causing harm: Start with WARNING alerts only for first week; enable auto-recovery gradually after validation
- Cron running health monitor itself causing loops: Exclude health-monitor from its own checks
- OpenRouter free tier unavailable: Fallback to simple pattern matching (regex) for error detection
- Log file locations change: Use config file for paths, keep checks modular

**Success Criteria:**
- 100% of critical failures detected within 30 minutes
- Auto-recovery success rate >80% for known issues
- No alert storms (rate limiting effective)
- Master receives ≤3 notifications per week (only true issues)
- Dashboard consistently reports accurate health score

     * Description: include original email link

     * Check duplicate handling and update logic
   - End-to-end: Full workflow on a controlled subset

   - Set up notifications:

   - Add to `HEARTBEAT.md`: Check quarantined items and parsing error count

**Feasibility Assessment:**
- ⚠️ Minor Master input needed: Provide exchange API keys (one-time)
- Once keys provided, fully autonomous
- No trading execution = no financial risk

**Detailed Implementation Steps:**

1. **Setup Phase (MASTER ACTION REQUIRED)** (Master: 15min to generate API keys; Claire: 2 hours)

   - Define signal types to detect:
     * Funding rate arbitrage (differences between futures exchanges)
     * Pairs trading (cointegrated assets)
     * Mean reversion (deviations from moving averages)
     * Order book imbalances (large buy/sell walls)
     * Volatility spikes (opportunities for options/perp strategies)
   - Define backtesting framework: Historical validation of signal concepts (simple, not full backtest engine)

     * REST API clients for market data (OHLC, funding rates, order book snapshots)

   - Implement data aggregation:
     * Daily OHLC fetch for all assets
     * Funding rate time series

   - Build caching layer: avoid re-fetching unchanged data
   - Add error handling: API downtime, rate limits, invalid keys

3. **Development Phase - Signal Engine** (8 hours)
   - Implement statistical analysis modules:
     * Pairs correlation and cointegration tests (ADF test)
     * Z-score spread monitoring for mean reversion
     * Moving average crossovers and bollinger band squeezes
     * Funding rate differential > threshold (spot vs futures, or cross-exchange)
     * Order book imbalance = (bids - asks) / (bids + asks) at top levels
   - Build signal scoring:
     * Confidence: based on statistical strength (p-values, spread magnitude)
     * Risk: volatility, liquidity, correlation
     * Reward: expected return based on historical patterns
     * Final score: weighted combination (0-100)
   - Implement signal filtering:
     * Minimum liquidity filter (avoid illiquid assets)
     * Maximum risk filter (discard high-risk unless very high confidence)
     * Diversification: not all signals on same asset
   - Create daily signal generation:
     * Run at 6AM SGT (pre-market)
     * Output top 3-5 signals with:
       - Asset and direction (long/short/arbitrage)
       - Confidence score and rationale
       - Suggested entry/exit levels
       - Risk metrics (stop loss, position size suggestion)
       - Chart image (simple candlestick with indicators)

4. **Development Phase - Reporting** (4 hours)
   - Generate Telegram digest:
     * Format: Markdown with clear sections per signal
     * Include small chart images (generate as PNG, send as photo if possible)
     * Links to exchange for manual execution
   - Store detailed report in `research/trading-signals/YYYY-MM-DD.md`
   - Create signal archive for tracking outcomes (manual feedback loop)
   - Build simple dashboard (optional): HTML page showing signal history and performance metrics (GitHub Pages)

5. **Testing Phase** (2 hours)
   - Run on historical data (last 30 days) to verify signals would have been interesting
   - Validate no API leaks, proper error handling
   - Check Telegram message formatting and chart generation
   - Simulate API failure and verify graceful degradation (use cached data)

6. **Deployment Phase** (1 hour)
   - Install as skill: `trading-researcher`
   - Configure cron: daily 6AM SGT
   - Set notification: Telegram only if >=1 signal with confidence >70
   - Add to `HEARTBEAT.md`: Brief review of yesterday's signals after market close
   - Create manual trigger command: `claw trading-researcher run` for on-demand

7. **Maintenance Phase** (ongoing, 2-3 hours/week)
   - Track actual outcomes: manually note which signals would have profited
   - Tune parameters (thresholds, weights) based on accuracy
   - Add new signal types as discovered
   - Monitor API usage and rate limits; rotate keys if needed
   - Monthly performance report: win rate, average R/R, Sharpe (rough)

**Potential Blockers & Mitigations:**
- Exchange API keys invalid: Validate on startup, send alert if auth fails; fallback to cached data mode (no new signals)
- Market data gaps: Use multiple exchanges; fill gaps with interpolation only for backtesting, not live signals
