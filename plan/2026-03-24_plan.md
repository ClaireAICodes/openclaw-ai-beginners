**Feasibility Assessment:**

   - Audit current backup script (`openclaw_backup.sh` or equivalent)
   - Identify all dependencies: `jq`, `gog`, `curl`, `tar`, `gpg`, network access
   - Design JSON log schema: timestamp, step, status, error_code, recovery_action
   - Create test harness to simulate missing dependencies and network failures

2. **Development Phase** (4 hours)

     - Verify `gog` binary in PATH; if missing, output clear instruction for brew install
   - Implement retry wrapper:
     - 3 attempts with exponential backoff (1s, 2s, 4s)
     - Capture and log each attempt's outcome
   - Enhance logging:
     - Replace echo statements with structured JSON to log file

     - Network timeout → verify retry logic
     - Corrupted backup → verify detection and alert
   - Review log output structure

4. **Deployment Phase** (1 hour)
   - Backup original script
   - Replace with enhanced version
   - Update cron job if needed (use absolute paths)
   - Run one-time smoke test

5. **Maintenance Phase** (ongoing)
   - Monitor logs weekly for any new failure patterns
   - Update retry thresholds if needed based on actual network reliability

**Potential Blockers & Mitigations:**
- **Sudo permissions:** Auto-apt-get may fail without passwordless sudo. Mitigation: detect and alert instead of attempting install.
- **Host restrictions:** If running in container, apt-get may not work. Mitigation: output explicit instructions for Master.
- **gog installation:** Requires Homebrew; can't auto-install. Mitigation: clear error message with install command.

**Success Criteria:**
- No backup failures due to missing dependencies

### 2. [Priority 2] System Health Monitor & Auto-Recovery (GREEN)

**Impact:** High | **Effort:** 2.5 days | **Confidence:** High

**Overview:**
A proactive watchdog that checks OpenClaw system health: cron job execution status, dependency versions, API connectivity, and disk space. It auto-recovers from common issues (restart failed services, reinstall missing packages) and escalates alerts for human intervention. Prevents silent failures across the automation ecosystem.

**Resource Requirements:**
- 🆓 Free hosting: None (local script with cron)
- 🆓 Free APIs/models: None
- 🧰 OpenClaw Skills needed: None (standalone health script)
- 💸 Costs: $0
- 🔑 Master must provide: None

**Feasibility Assessment:**
- ✅ Can build autonomously with current resources

**Detailed Implementation Steps:**

1. **Setup Phase** (3 hours)
   - Inventory all critical components:
     - Cron jobs: list, schedule, expected run times
     - Dependencies: Node.js modules, CLI tools (`gog`, `jq`, `gh`, `openclaw` CLI)
     - Services: gateway daemon, any background agents
     - Storage: disk usage thresholds (warning >80%, critical >90%)
   - Define health check functions for each component
   - Design alert routing: Telegram for critical, log file for warnings

2. **Development Phase** (6 hours)
   - Build health check modules:
     - `check_cron()`: parse `crontab -l` and `/var/log/cron` to verify recent executions; flag jobs that didn't run in expected window
     - `check_dependencies()`: verify versions of Node, npm modules, CLI tools; report outdated or missing
     - `check_services()`: `systemctl status openclaw-gateway` or process check; attempt restart if failed
     - `check_disk()`: `df -h` on critical partitions
     - `check_network()`: ping reliable hosts (8.8.8.8, google.com)
   - Implement auto-recovery actions:
     - Restart gateway: `openclaw gateway restart`
     - Reinstall npm module: `npm install -g <package>`
     - Clear temp files if disk low
   - Build reporting:
     - Generate markdown status file: `health/status.md`
     - Send Telegram message if any critical issues or after auto-recovery
   - Add config file `health/config.json` to set thresholds and enable/disable checks

3. **Testing Phase** (3 hours)
   - Simulate failures:
     - Stop gateway → verify detection and restart
     - Remove `jq` → verify alert
     - Fill disk (or mock) → verify cleanup attempt
     - Disable a cron job → verify detection
   - Review alerts and auto-recovery logs

4. **Deployment Phase** (2 hours)
   - Install health script to `/home/node/.openclaw/scripts/health_monitor.sh`
   - Add cron job: run every 15 minutes via `crontab -e`
   - Create initial status directory: `mkdir -p /home/node/.openclaw/workspace/health`
   - Run first check manually to verify setup

5. **Maintenance Phase** (ongoing)
   - Weekly review of health logs to tune thresholds
   - Update component list as new services/crons are added

**Potential Blockers & Mitigations:**
- **Permission issues:** Systemctl restart may need sudo. Mitigation: detect and alert Master; perhaps configure passwordless sudo for specific commands.
- **Cron log parsing:** Log format varies by system. Mitigation: use `systemctl status cron` or check job exit codes via wrapper scripts.
- **False positives:** Transient network glitches. Mitigation: require 2 consecutive failures before critical alert.

**Success Criteria:**
- Health status file updates every 15 minutes
- Telegram alerts sent for critical issues within 1 minute of detection
- Auto-recovery clears at least 80% of common issues without human intervention
- Master receives weekly summary of system health (optional)
